# Workflow

## Read Order
1. `Haruta_dev/HarutaAGENTS.md`
2. 関連する `Haruta_dev/policies/`
3. `Haruta_dev/workflow.md`
4. command-based の話なら `Haruta_dev/reference/wpilib-command-based.txt`
5. 必要に応じて `Haruta_dev/ROADMAP.md`
6. 必要に応じて `Haruta_dev/PROJECT_OVERVIEW.md`
7. 必要に応じて `Haruta_dev/FILE_MAP.md`
8. 公式情報が必要なら `Haruta_dev/reference/`

## Flow
1. 目的と完了条件を整理する
2. `Read Order` に従って必要な文書を読む
3. 最低限守るルールを短く見直す
4. 関連コードと公式資料を確認する
5. 対象ファイルの担当表記を確認する
6. 設計整理フェーズか、コード提案フェーズかを明確にする
7. 世界レベルの制御と安全性の観点で、fallback と fail-safe を確認する
8. 変更候補、参照のみ、確認待ちのファイルを分ける
9. 新規ファイルが必要かを厳しめに見直す
10. コード提案が必要なら、1変更ずつ順番に提案する
11. 既存ファイルでは、全文ではなく差分だけを出す
12. 各変更ブロックに、何行目付近かと、どのコードの中、下、上に入れるかを付ける
13. 変更前コードは出さず、変更後コードだけを出す
14. 各変更ごとに、理由と反映後の挙動を短く説明する
15. コメントはコードの上に置く前提で提案する
16. Haruta が反映する
17. 検証内容と結果をまとめる
18. コード提案を出した場合だけ `Haruta_dev/AGENT_CODE_HISTORY.md` に履歴を残す
19. 次にやることを明確にする
20. chat の最後にロードマップを付ける
21. chat の最後に、Haruta が次にやるタスクを短く出す

## Explanation Rule
- ファイルの役割を聞かれたら、そのファイル単体ではなく関連ファイルも含めて説明する
- 挙動を説明するときは、入力、処理、出力、関連 subsystem や command をセットで説明する
- 数式やロジックは、式だけでなく意味も説明する
- 確認済み情報、コード読解による理解、推測は分けて説明する
- 公式ドキュメント由来の情報と、アイディア参考元の情報は分けて説明する

## Code Understanding Time
1. Haruta が `コード理解タイム` と宣言する
2. AGENT はロジック変更案ではなく、理解用コメント案を優先する
3. コメントは対象コードの上に置く形で提案する
4. 1回に1変更だけ出して、短く説明する
5. Haruta が反映しながらコードを読む
6. 必要なら次のコメント案へ進む

## Handoff Format
- 何をやるか
- どこを触るか
- 何をもって完了か
- 残っている不明点
- 次に何をするか

## Validation Flow
1. 実装案または変更案を整理する
2. Haruta が反映する
3. ある程度まとまったら SIM フェーズに入る
4. 起動方法、確認項目、期待結果、実結果を整理する
5. 問題があれば原因候補を切り分ける
6. 安全に止まる条件、fallback 条件、再試行条件を確認する

## Rule Update Flow
1. Haruta が新しいルールを追加する
2. `Haruta_dev/` 内に既存の記載があるか確認する
3. あれば正本だけを更新し、他ファイルへ重複記載しない
4. なければ適切なファイルへ追加する
5. 矛盾がある場合は Haruta に確認する
