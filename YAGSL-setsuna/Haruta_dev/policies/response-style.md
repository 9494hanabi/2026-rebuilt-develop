# Response Style

## Codex App
- 回答はとにかくわかりやすくする
- 情報は常に整理して提示する
- 確実な情報源から取ってきた情報を優先する
- 固定観念で決め打ちせず、「これはどうだろう」「別の可能性はあるか」を能動的に考える
- 回答スタイルに細かい固定形は持ちすぎず、Haruta の要望に応じてその都度調整する

## Codex App Output Preference
- 結論を先に出す
- 情報はまとまりごとに分ける
- 確認済み情報、コード読解、推測は混ぜずに説明する
- 使った情報源を毎回示す
- 最後に現在地がわかるロードマップを付ける
- 最後に Haruta が次にやるタスクを短く付ける

## AGENT
- プログラム提案は何のコードかわかるようにコメントを付ける
- 一文の短い説明は `//` を使う
- 二文以上、補足、箇条書きになりそうな説明は `/* ... */` を使う
- まとまりごとに `// 以下PathPlannerのコード` のような見出しコメントを付けて、読みやすくする
- コメントは「何をしているか」「なぜ必要か」が分かる内容を優先する
- コメントは対象コードの横ではなく、上に書く
- コメント位置は上寄せで統一する

## AGENT Proposal Preference
- 変更案を出す前に対象ファイルを明示する
- コードだけでなく、変更理由も短く付ける
- ロジックが難しい場合は、計算の意味まで説明する
- ファイル参照はクリックしやすい形で明示する
- どこに差し込むかを、何行目付近かと既存コードのアンカーで分かりやすく示す
- 「追加」「置換」「追記」「新規作成」を明示する
- 既存コードを置き換える場合は、どのメソッドやブロックを置き換えるのかを明示する
- コード提案は、Haruta がそのまま反映しやすいまとまりで出す
- 既存ファイルの提案では、全文ではなく変更箇所だけを出す
- 未変更コードは、位置特定に必要な最小限だけ示す
- 差分が複数ある場合でも、まず1変更ずつ順番に出す
- コピペだけの全文置換に誘導する出し方は避ける
- 「どのファイルのどのコードの下や中に何を入れるか」が一目で分かる形を優先する
- 「どのファイルの何行目付近に、どのコードの下や中に何を入れるか」が一目で分かる形を優先する
- 変更前コードは原則として出さない
- 変更後コードだけを出す
- 解説は難しい言葉を詰め込みすぎず、短く区切って分かりやすくする
- Haruta が `コード理解タイム` と言ったら、理解用コメント追加を優先する
- `コード理解タイム` では、ロジック変更より「何をしているコードか」を説明するコメント案を出す

## Preferred Code Proposal Structure
1. 対象ファイル
2. 対象行
3. 操作種別
4. 差し込み位置または置換位置
5. 変更理由
6. 提案コード
7. 反映後どうなるか
8. 反映後に確認すること

## Code Understanding Structure
1. 対象ファイル
2. 対象行
3. 差し込み位置
4. このコードが何をしているか
5. 追加コメント
6. 読んだあとに分かるようになること
