# Edit Policy

## Codex App
- Codex app が編集できるのは `Haruta_dev/` 配下のみ
- `Haruta_dev/` 配下であっても、変更前に Haruta の確認を取る
- `Haruta_dev/` 以外は閲覧、整理、説明、提案のみ
- `Haruta_dev/` 外の変更が必要だと判断した場合は、変更せずに提案だけ出す
- コードベース側の提案では、担当が Haruta のファイルだけを対象にする
- 担当が他の人なら、編集案を進める前に Haruta に知らせる
- 担当不明のファイルは、確認が取れるまで編集案の対象にしない

## AGENT
- AGENT はプログラムを直接変更しない
- AGENT は変更案を chat に貼る
- 実際の変更は Haruta が行う
- AGENT は勝手に削除しない
- AGENT は Haruta が担当のファイルだけを変更候補として扱う
- AGENT はコード提案にコメントを入れて、何の塊かを分かるようにする
- AGENT は既存ファイルの全文コードを貼らない
- AGENT は変更が必要な部分だけを最小単位で提案する
- AGENT は未変更部分を大量に再掲しない
- AGENT は1回の提案で1変更を基本とする
- AGENT は複数変更が必要でも、まず最初の1変更から出す
- AGENT は新規ファイルを安易に増やさない
- 新規ファイルを提案する場合は、既存ファイルへ入れない理由を明示する
- AGENT は読みにくい長いファイル名や変数名を避ける
- AGENT は短くて意味が通る命名を優先する
- AGENT は命名が長すぎる場合、より短くて分かりやすい代案を提案する

## Change Proposal Format
- 対象ファイル
- 対象行
- 操作種別
- 差し込み位置
- 変更理由
- 変更内容
- 影響範囲
- 確認方法

## Change Proposal Detail Rule
- 対象ファイルは、毎回フルパスまたは明確な相対パスで示す
- 対象行は、必ず `xx行目付近` の形で示す
- 差し込み位置は、既存コードの中、直前、直後のどれかが分かる形で示す
- 行番号だけではズレるので、アンカーコードも必ず併記する
- 毎回、次のどれをするのか明示する
  - 新規追加
  - 既存コードの置換
  - 既存コードの直後に追記
  - 既存コードの直前に追記
  - ファイル新規作成
- 「ここに入れてください」だけで終わらせず、どのコードの中か、どのコードの下かまで示す
- 変更案のコードは、可能な限りそのまま貼り付けられる単位で出す
- 既存ファイルでは、変更点だけを抜き出して出す
- 既存コードの全文表示は避け、前後の最小アンカーだけを添える
- 1つのファイルで複数箇所を変える場合でも、原則1変更ずつ提案する
- 全文を出してよいのは、新規作成ファイルを提案する場合だけとする
- 変更前コードは原則として出さない
- 変更後コードだけを出し、どこに入れるかを簡潔に示す
- 置換提案では、置換対象のメソッド名、ブロック名、定数群名などを明示する
- 追記提案では、次の順で出す
  - 対象ファイル
  - 対象行
  - 操作種別
  - 差し込み位置
  - 変更理由
  - 追加コード
- 置換提案では、次の順で出す
  - 対象ファイル
  - 対象行
  - 操作種別
  - 差し込み位置
  - 変更理由
  - 変更後コード
- 各提案では、次の変更へ勝手に進まず、まず今の変更を反映できる状態にする
